**Architectural Philosophy**: Config-based modularity, inspired by Anton Ukhanev's "Cross-Platform Modularity in PHP" and Dhii container/service patterns. Concrete building blocks in new project are **packages** and **providers**. Avoid overloaded JavaScript term "module" unless explicitly talking about ES/CommonJS modules. Provider = set of keyed definitions and extensions. Providers have no lifecycle. Host (CLI) owns composition, ordering, and runtime bridging. All behavior emerges from keyed lazy definitions, extensions, deterministic composition order, and one composed immutable source of truth.

## What This Tool Does

The new runner is a **command-line tool for driving a mobile app through natural language steps**. A developer or agent writes plain Gherkin-style sentences — `click "Login"`, `type "hello@example.com" in "Email"`, `I should see "Welcome"` — and the runner executes them against a real or emulated device over Appium/WebDriverIO.

### Primary use

```bash
# Run a feature file
uny run tests/features/login.feature

# Pipe ad-hoc commands from stdin (interactive or scripted)
uny run <<< 'click "Login"'

# Chain flows preserving app state
uny run tests/features/smoke.feature
uny run --reset none tests/features/login.feature

# Force a fresh session
uny run --new-session tests/features/smoke.feature
```

### What the tool manages

- **Session**: a persistent WebDriverIO/Appium connection that survives across invocations. The runner attaches to an existing live session or creates a new one. If the session dies mid-run, steps recover automatically.
- **App reset**: at scenario boundaries the runner can hard-reset (close + clear data + launch), soft-reset (close + launch), or leave the app untouched — controlled per run via `--reset`.
- **Lock**: prevents accidental parallel runs via a lock file. A `--force` flag clears stale locks.
- **Output**: human-readable emoji hierarchy to stdout (TTY-aware, in-place updates); structured NDJSON to a log file in parallel. Verbosity is a single integer scale from -3 (silent) to +3 (trace).

### Verbosity scale

| Flag       | Level | What you see                |
| ---------- | ----- | --------------------------- |
| `-q -q -q` | -3    | nothing (exit code only)    |
| `-q -q`    | -2    | errors only                 |
| `-q`       | -1    | errors + warnings           |
| (default)  | 0     | notices + warnings + errors |
| `-v`       | 1     | +infrastructure info        |
| `-v -v`    | 2     | +debug detail               |
| `-v -v -v` | 3     | +raw trace / Appium logs    |

### Secondary commands

```bash
uny tree                          # Print accessibility tree of current screen
uny tree --format json            # Export tree as JSON
uny screenshot                    # Capture screen
uny reset --hard                  # Reset app state without a run
uny inspect <key>                 # Show DI container key resolution chain
```

### Who uses it

- **Developers** writing and debugging feature flows locally
- **CI pipelines** running feature files headlessly against an emulator
- **AI agents** driving the app as part of automated test generation or autonomous QA — the stdin mode and structured log output are designed for machine consumption

### Step patterns

Steps are matched by a custom Gherkin expression engine. The 42 standard mobile step patterns (tap, type, swipe, assert visibility, etc.) ship as a separate external package and are composed in. New step patterns can be added by any provider without modifying the runner core.

## 1. Core Principles

### 1.1 A Provider Is Its Configuration

A provider contributes behavior through composed configuration, not by mutating global state or calling host APIs directly. It is represented by keyed definitions (factories) and extensions (decorators). Provider has no setup, boot, or run phase. All behavior — services, handlers, commands, adapters, pipelines, policies — is expressed as values under keys.

### 1.2 The Six Primitives

The entire architecture arises from six primitives:

1. **Keyed lazy definitions** — A function `(container) => value` associated with a key. Evaluated on first access, not at composition time.
2. **Extensions** — A function `(previousValue, container) => newValue` that layers behavior onto an existing key without replacing its definition.
3. **Deterministic composition order** — Providers are composed in a host-specified order. Later definitions for the same key replace earlier ones. Extensions for the same key compose in source order.
4. **Override semantics** — The last definition wins for any key.
5. **Extension semantics** — Extensions chain in provider order; each receives the previous resolved value.
6. **One composed source of truth** — A single immutable container. Once composed, it does not change.

### 1.3 What Emerges From These Primitives

Everything else is built from the six primitives — no separate extension mechanisms needed:

| Pattern                  | How It Works                                                     |
| ------------------------ | ---------------------------------------------------------------- |
| **Overrides**            | Later provider defines same key → replaces earlier definition    |
| **Integration bindings** | Alias definition maps one provider's key to another's            |
| **Debug wrappers**       | Extension wraps existing service with tracing/logging            |
| **Feature composition**  | Host includes/excludes providers → adds/removes definitions      |
| **Handler pipelines**    | Key holds pipeline; providers contribute handlers via extensions |
| **List services**        | Key holds array; providers append via extensions                 |
| **Scoped views**         | Container wrapper strips/adds key prefixes                       |

### 1.4 Design Checklist

- [ ] Providers are definition/extension sources with no lifecycle
- [ ] Host decides provider selection and order
- [ ] One composed source of truth for resolved values
- [ ] Overrides and extensions have distinct, documented semantics
- [ ] Load order is deterministic and visible
- [ ] Missing dependencies are key references, not hidden globals
- [ ] Platform integration adapted by host into keys
- [ ] Keys are namespaced to avoid collisions
- [ ] Bindings between providers are explicit and diagnosable
- [ ] Definitions are lazy (resolved on access, not composition time)
- [ ] Composed configuration is immutable once loaded
- [ ] List services used where multiple modules contribute to a collection
- [ ] Debug behavior modeled as ordinary definitions/extensions
- [ ] Feature selection happens at composition time (provider set), not runtime flag checks

## 2. What This Tool Does

Uny is an **exploration-first mobile app testing CLI**. Unlike traditional test runners that execute full suites, uny lets users run individual commands against a real mobile device, with session persistence between invocations.

### Core Capabilities

1. **Session Persistence** — WebDriverIO session created once, persisted to JSON file (`.e2e-active-session`). Subsequent invocations attach to existing session (<1s vs 30s+ restart). Session file: `{id, url, capabilities, createdAt}`. Lifecycle: `create()` via `remote()`, `attach()` via `attach()`, `isAlive()` via `browser.getTimeouts()`. Auto-recovery on SessionDeathError (ECONNREFUSED, ECONNRESET, ETIMEDOUT, "not reachable", "session not found").

2. **Gherkin + Raw Command Parsing** — Strips keywords (Given/When/Then/And/But), strips leading "I ", routes through sentence registry using custom expression matching (`{string}`, `{word}`, `{int}` placeholders) + regex patterns wrapped in `/pattern/`. No Cucumber dependency.

3. **Multi-Strategy Element Discovery** — Click resolution (2-pass): preferred (clickable + description/text/contains) → fallback (any element). Input resolution (4-strategy): semantic field (hint/text/desc on EditText) → spatial proximity (label above, EditText below, score formula) → direct EditText selectors → fallback.

4. **Device Abstraction** — OS operations (closeApp, clearData, launchApp, command) behind interface. Android: `docker exec <container> adb shell <cmd>`. iOS: stub.

5. **Accessibility Tree Visualization** — Parse XML page source via xml2js, filter (minimal/default/full), compute visibleDepth, format as human tree/JSON/XML.

6. **Unified Verbosity** — Scale -3 to +3, default 0. `-v` increments, `-q` decrements. `notice()` → stdout (machine-parseable), everything else → stderr (diagnostics).

7. **File-Based Locking** — `.runner.lock` JSON with PID, start time, run ID. Atomic creation `{flag:'wx'}`. Stale lock (dead PID) clearable with `--force`.

8. **Reset Modes** — At Scenario boundaries: `hard` (terminate + clear data + relaunch), `soft` (terminate + relaunch), `none` (keep state).

9. **Stdin Mode** — `echo 'click "Login"' | uny run`. AI/pipe-driven exploration.

10. **Output Formats** — Human-readable (emoji status) or JSON array. Auto-tree and auto-screenshot appendable per step.

## 4. Provider Shape and Composition Library

### 4.1 Provider Type

```typescript
/** A factory that lazily produces a value when the key is resolved */
type Definition<T = unknown> = (container: Container) => T;

/** A decorator that receives the previous value and returns a modified value */
type Extension<T = unknown> = (
  previous: T | undefined,
  container: Container,
) => T;

/** A module's entire contribution to the system */
interface Provider {
  readonly definitions?: Record<string, Definition>;
  readonly extensions?: Record<string, Extension>;
}
```

Providers don't have intrinsic names. The host assigns names when composing for diagnostic purposes.

### 4.1.1 Idiomatic Definition Types (inspired by `dhii/services`)

Raw `(container) => value` factories are verbose. Like `dhii/services`, we provide helper functions that:

- Declare dependencies as key arrays (enables static dependency graph analysis)
- Auto-resolve dependencies before passing to callback (no manual `c.resolve()`)
- Return `DependencyAwareDefinition` with `getDependencies()` for static analysis

```typescript
// Instead of verbose:
'session/manager': (c) => {
  const persistence = c.resolve<SessionPersistence>('session/persistence');
  const config = c.resolve<E2EConfig>('config/loaded');
  const deathPatterns = c.resolve<RegExp[]>('session/death-patterns');
  return createSessionManager({ persistence, config, deathPatterns });
},

// Idiomatic (like dhii/services Factory):
'session/manager': factory(
  ['session/persistence', 'config/loaded', 'session/death-patterns'],
  (persistence: SessionPersistence, config: E2EConfig, deathPatterns: RegExp[]) =>
    createSessionManager({ persistence, config, deathPatterns })
),

// Constructor shorthand:
'screen/tree-formatter': construct(TreeFormatter),

// Value shorthand:
'io/verbosity': value(0),

// Alias shorthand:
'device/platform': alias('config/loaded'),
```

Definition types: `factory()`, `construct()`, `value()`, `alias()`. All return `DependencyAwareDefinition` (a `Definition` with `getDependencies(): string[]` attached) for static analysis.

### 4.2 Container Type

```typescript
interface Container {
  /** Resolve a key to its value. Lazy: factory runs on first access, cached thereafter. */
  resolve<T = unknown>(key: string): T;
  /** Check if a key has a definition or extension */
  has(key: string): boolean;
  /** Diagnostic: return source info for a key (which module defined it, which extended it) */
  inspect(key: string): KeyInspection;
  /** List all registered keys */
  keys(): string[];
}

interface KeyInspection {
  key: string;
  /** Full override chain in composition order (not just the winner) */
  definitionChain: Array<{ sourceName: string; overridden: boolean }>;
  /** The winning definition source (last in chain) */
  definedBy: string | null;
  /** Extension sources in composition order */
  extendedBy: string[];
  resolved: boolean;
  cachedValue?: unknown;
}
```

### 4.3 Composition Algorithm

Composition internals are implementation details — no exported interface. The `composeProviders` function returns an opaque result consumed only by `createDelegatingContainer`.

```typescript
// Internal type — NOT exported. Composition is an implementation detail.
type ComposedDefinitions = {
  definitions: Map<string, { factory: Definition; sourceName: string }>;
  /** Full chain of all definitions per key (for override chain inspection) */
  definitionHistory: Map<
    string,
    Array<{ factory: Definition; sourceName: string }>
  >;
  extensions: Map<string, Array<{ extension: Extension; sourceName: string }>>;
};

function composeProviders(
  providers: Map<string, Provider>,
): ComposedDefinitions {
  const composed: ComposedDefinitions = {
    definitions: new Map(),
    definitionHistory: new Map(),
    extensions: new Map(),
  };

  for (const [name, provider] of providers.entries()) {
    // Later definitions override earlier ones (override semantics)
    if (provider.definitions) {
      for (const [key, factory] of Object.entries(provider.definitions)) {
        composed.definitions.set(key, { factory, sourceName: name });
        // Track full override chain for diagnostics
        const history = composed.definitionHistory.get(key) ?? [];
        history.push({ factory, sourceName: name });
        composed.definitionHistory.set(key, history);
      }
    }
    // Extensions accumulate in provider order (extension semantics)
    if (provider.extensions) {
      for (const [key, extension] of Object.entries(provider.extensions)) {
        if (!composed.extensions.has(key)) composed.extensions.set(key, []);
        composed.extensions.get(key)!.push({ extension, sourceName: name });
      }
    }
  }

  return composed;
}
```

The host supplies names when composing. This keeps providers pure — they're just data structures.

### 4.4 Container Creation — Separated Concerns

Following `dhii/containers`, the container is decomposed into single-responsibility decorators:

- **`DelegatingContainer`** — Resolves keys by invoking factories/extensions from a composed provider. No caching. Accepts an optional parent container for lookup delegation.
- **`CachingContainer`** — Decorator that caches resolved values. Wraps any container.
- **`CompositeContainer`** — Merges multiple containers (e.g., config from DB + config from modules). First container with the key wins.
- **`ProxyContainer`** — Forwards to an inner container that can be assigned after construction. Solves circular lookup delegation.

```typescript
// DelegatingContainer — resolves from composed provider, delegates lookup to parent
function createDelegatingContainer(
  composed: ComposedDefinitions,
  parent?: Container,
): Container {
  const lookup = parent ?? self; // lookup delegation
  const resolving = new Set<string>();

  const self: Container = {
    resolve<T>(key: string): T {
      if (resolving.has(key)) {
        throw new CircularDependencyError(key, [...resolving]);
      }
      const defEntry = composed.definitions.get(key);
      const exts = composed.extensions.get(key) ?? [];
      if (!defEntry && exts.length === 0) {
        throw new MissingKeyError(key, [...composed.definitions.keys()]);
      }
      resolving.add(key);
      try {
        let value: unknown = defEntry ? defEntry.factory(lookup) : undefined;
        for (const ext of exts) {
          value = ext.extension(value, lookup);
        }
        return value as T;
      } finally {
        resolving.delete(key);
      }
    },
    has(key) {
      return composed.definitions.has(key) || composed.extensions.has(key);
    },
    inspect(key) {
      /* see KeyInspection below */
    },
    keys() {
      /* sorted union of def + ext keys */
    },
  };
  return self;
}

// CachingContainer — decorator, separate concern
function createCachingContainer(inner: Container): Container {
  const cache = new Map<string, unknown>();
  return {
    resolve<T>(key: string): T {
      if (cache.has(key)) return cache.get(key) as T;
      const value = inner.resolve<T>(key);
      cache.set(key, value);
      return value;
    },
    has: (key) => inner.has(key),
    inspect: (key) => ({
      ...inner.inspect(key),
      resolved: cache.has(key),
      cachedValue: cache.get(key),
    }),
    keys: () => inner.keys(),
  };
}

// Typical bootstrap wiring (like dhii/containers example):
const proxy = createProxyContainer();
const delegating = createDelegatingContainer(composed, proxy);
const cached = createCachingContainer(delegating);
proxy.setInner(cached); // lookup delegation now goes through cache
```

## 6. Provider Catalog

Each provider lives in its own file and exports a `Provider` object. No classes, no lifecycle methods, no framework coupling.

Providers are organized around **application concerns**, not domains. One provider may span multiple domains if they form one cohesive application concern. For example, element discovery and accessibility tree parsing are both about understanding and interacting with what is on screen.

### 6.2 Provider: `config`

Hierarchical configuration resolution. Two layers compose into one source of truth:

```
defaults (from provider)  ←  JSON config file  ←  CLI flags (override provider)
```

**No Cosmiconfig.** Just a plain `.e2erc.json` file, natively importable. JSON config values can reference environment variables using `${ENV_VAR}` syntax (like Docker Compose), resolved at load time. No separate env-var layer.

**No Zod.** Config validation uses JSON Schema, which can be consumed by any validation tool (ajv, etc.) and doubles as documentation.

```typescript
export const configProvider: Provider = {
  definitions: {
    'config/schema': () => configJsonSchema, // JSON Schema object (see Section 8)

    'config/defaults': () => ({
      platform: 'android',
      sessionFile: '.e2e-active-session',
      lockFile: '.runner.lock',
      outputDir: './output',
      wdio: {
        hostname: 'localhost',
        port: 4723,
        path: '/',
        logLevel: 'silent',
        connectionRetryTimeout: 120000,
        connectionRetryCount: 3,
      },
      reset: {
        hard: { closeApp: true, clearData: true, launchApp: true },
        soft: { closeApp: true, clearData: false, launchApp: true },
        none: { closeApp: false, clearData: false, launchApp: false },
      },
    }),

    // Layer 2: JSON config file with ${ENV_VAR} reference resolution
    'config/from-file': () => {
      const filePath = findConfigFile(); // looks for .e2erc.json
      if (!filePath) return {};
      const raw = JSON.parse(fs.readFileSync(filePath, 'utf-8'));
      return resolveEnvReferences(raw);
      // resolveEnvReferences: walks object, replaces "${VAR}" with process.env.VAR
    },

    // Layer 3: CLI flags — injected by host as override provider (see Section 7)
    'config/from-cli': () => ({}), // default empty, host overrides this

    // Composed: merge all layers, validate with JSON Schema
    'config/loaded': (c) => {
      const schema = c.resolve<object>('config/schema');
      const defaults = c.resolve<object>('config/defaults');
      const fromFile = c.resolve<object>('config/from-file');
      const fromCli = c.resolve<object>('config/from-cli');
      const merged = deepMerge(defaults, fromFile, fromCli);
      validateJsonSchema(schema, merged); // throws on invalid
      return merged as E2EConfig;
    },
  },
};
```

Cosmiconfig, YAML, env-var layers etc. can be added later if needed — just add a provider that overrides `config/from-file`.

### 6.5 Provider: `logging`

#### Design principles

**Separation of concerns**: implementation services (session, device, steps, etc.) must not import or call the logger directly. They receive typed interfaces injected via the container. The optional `debug` provider (6.5.3) decorates those services with logging via **extensions** — the implementations never know logging is happening.

**No logger calls in business logic.** `SessionManager`, `DeviceAdapter`, `StepRunner`, etc. are plain implementations. Logging wraps them externally via provider extensions on the same keys.

#### 6.5.1 Core logger

Single `Logger` interface with verbosity-gated methods. Injected only where truly needed (output formatter, CLI progress display).

```
notice() → stdout  (verbosity >= 0, default on)
info()   → stderr  (verbosity >= 1)
debug()  → stderr  (verbosity >= 2)
trace()  → stderr  (verbosity >= 3)
warn()   → stderr  (verbosity >= -1)
error()  → stderr  (verbosity >= -2, always on except at -3 absolute silence)
```

#### 6.5.2 Output sinks and composite logger

Two channels run in parallel: **human display** (stdout, TTY-aware) and **structured log** (file, always NDJSON). A `CompositeLogger` fans writes out to whichever sinks are configured:

```typescript
interface Logger {
  notice(msg: string, ...args: unknown[]): void;
  info(msg: string, ...args: unknown[]): void;
  debug(msg: string, ...args: unknown[]): void;
  trace(msg: string, ...args: unknown[]): void;
  warn(msg: string, ...args: unknown[]): void;
  error(msg: string, ...args: unknown[]): void;
}
```

**Human sink** (stdout): TTY → in-place carriage-return updates with frozen `[MM:SS]` timestamp, emoji hierarchy. Non-TTY → plain newline-separated lines with real timestamps.

**JSON sink** (file): NDJSON — one JSON object per line, no surrounding `[`/`]`. Each line is independently parseable by `jq`. Example:

```
{"ts":12,"level":"notice","msg":"✅ click \"Login\""}
{"ts":14,"level":"error","msg":"❌ element not found"}
```

**Log file**: single NDJSON file per run (`run-{id}.ndjson`). Simple, all events in one place. Per-step files are an optional extension not in scope for initial build.

```typescript
export const loggingProvider: Provider = {
  definitions: {
    'log/human-sink': factory(
      ['io/stdout', 'io/verbosity'],
      (stdout, verbosity) => createHumanSink(stdout, verbosity),
    ),
    'log/json-sink': factory(['config/loaded'], (config: E2EConfig) =>
      config.logFile ? createJsonSink(config.logFile) : null,
    ),
    logger: factory(
      ['log/human-sink', 'log/json-sink', 'io/verbosity'],
      (humanSink, jsonSink, verbosity) =>
        createCompositeLogger(verbosity, [humanSink, jsonSink].filter(Boolean)),
    ),
    'output/format': value('human' as const),
    'output/formatter': factory(
      ['output/format', 'screen/tree-formatter', 'logger'],
      (format, treeFormatter, logger) =>
        createOutputFormatter(format, treeFormatter, logger),
    ),
  },
};
```

#### 6.5.3 Provider: `debug` (optional, composable)

A separate `debugProvider` adds logging **around** existing services via **extensions**. It does not touch implementations — it wraps resolved values. Included in the provider map only when wanted (e.g. always in dev, flag-gated in prod).

```typescript

  extensions: {
    'session/manager': (manager, c) =>
      wrapWithLogging(manager, c.resolve<Logger>('logger'), 'session'),
    'step/runner': (runner, c) =>
      wrapWithLogging(runner, c.resolve<Logger>('logger'), 'step'),

  },

```

Host includes it to enable tracing. No implementation code changes:

```typescript
providers.set('debug', debugProvider);
```

This satisfies the concern: logging is cross-cutting, added externally, implementations stay clean.

## 7. Bootstrap Flow

The CLI entry point is the host. It owns every step of composition.

```typescript
// bin/uny.ts — the host application
async function main() {
  // 1. Parse CLI flags (before composition — these inform provider selection and overrides)
  const cliFlags = parseCLIFlags(process.argv);

  // 2. Decide provider set and explicit order — host assigns names for diagnostics
  const providers = new Map<string, Provider>([
    ['core', coreProvider],
    ['config', configProvider],
    ['session', sessionProvider],
    ['device-android', deviceAndroidProvider],
    ['logging', loggingProvider],
    ['screen', screenProvider],
    ['steps', stepsProvider],
    ['cli', cliProvider],
  ]);

  // 2a. Feature selection via provider inclusion — not runtime flags
  // debug provider: wraps services with trace logging via extensions, no code changes to implementations
  if (cliFlags.debug || process.env.UNY_DEBUG) {
    providers.set('debug', debugProvider);
  }

  // 2b. CLI overrides as final provider (highest precedence in config hierarchy)
  providers.set('cli-overrides', {
    definitions: {
      'io/verbosity': () => cliFlags.verbose - cliFlags.quiet,
      'output/format': () => cliFlags.format ?? 'human',
      'config/from-cli': () => {
        const overrides: Record<string, unknown> = {};
        if (cliFlags.config) overrides._configPath = cliFlags.config;
        if (cliFlags.appId) overrides.appId = cliFlags.appId;
        if (cliFlags.resetMode)
          overrides.reset = { [cliFlags.resetMode]: true };
        return overrides;
      },
    },
  });

  // 3. Compose providers (override/extension order locked)
  const composed = composeProviders(providers);

  // 4. Create container (lazy resolution, caching)
  const container = createContainer(composed);

  // 5. Resolve CLI command and execute
  const commandName = cliFlags.command ?? 'run';
  const handler = container.resolve<Function>(`cli/command/${commandName}`);
  await handler(cliFlags);
}
```

**Terminology**: Provider is application-level unit. JS/TS module is only source file that exports provider value. Host explicitly imports each file and maps provider to diagnostic name. No magic discovery.

**Key properties:**

- Provider order explicit and visible in one place
- Config resolution is hierarchical: `defaults ← file ← CLI` (Section 6.2)
- CLI flags injected as the last provider — they override everything
- `debug` provider optionally composed in — wraps services with trace logging via extensions, zero coupling to implementations
- Container immutable once created
- All resolution lazy — unused services never instantiated

## 7b. Docker Distribution and Runtime JS Extensibility (Phase 2 summary)

Uny ships as a publishable image (`ghcr.io/xedinunknown/uny-core`). Projects **extend it at runtime by placing a single `uny.config.js` in their project root — no Uny rebuild required.**

There is no separate config resolution layer. The provider map **is** the config mechanism. A project's `uny.config.js` adds providers that define whatever keys they need — appId, platform, custom steps, overrides — same as any built-in provider.

### The transform hook

`uny.config.js` exports a **transform function** `(providers) => providers`. The host loads it via dynamic `import()` at startup, applies it to a copy of the ordered base provider map, then appends `cli-overrides` last (flags always win):

```
base map → user transform → cli-overrides LAST → composeProviders → bootstrap
```

The transform receives the full ordered `Map<string, Provider>` and returns a new map. It can append, insert between existing providers, replace, or remove. Full extension/override semantics apply because the result flows through `composeProviders` unchanged. Plain `Provider` object exports are accepted as sugar (auto-wrapped into an append-transform).

### Three delivery modes

**Bind-mount (dev):** `docker run --rm -v "$PWD":/project ghcr.io/xedinunknown/uny-core:latest inspect`

**Derived image (CI):** `FROM ghcr.io/xedinunknown/uny-core:latest` + `COPY uny.config.js /project/`

**Compose service:** mount project dir as `/project` in `docker-compose.yml`.

If `uny.config.js` imports npm packages, mount `node_modules` alongside it.

See full details: `.opencode/plans/1781997215265-phase-2-cli-config-docker.md`

## 10. Step Definitions — All 42 Patterns

### 10.1 Complete Pattern List

**Click:** `click {string}`, `click {word}`

**Type:** `type {string} in {string}`, `type {string} in {word}`, `type {word} in {string}`, `type {word} in {word}`

**Scroll:** `scroll {word}` (up/down/left/right)

**Scrollwheel:** `scrollwheel {word}`, `scrollwheel {word} by {int}`, `scrollwheel {word} {int} times`, `scrollwheel {word} in {string}`, `scrollwheel {word} in {string} by {int}`, `scrollwheel {word} in {string} {int} times`, `scrollwheel {string} to {int}`, `scrollwheel {word} to {int}`

**Set:** `set scrollwheel to {int}`, `set scrollwheel {string} to {int}`, `set scrollwheel {word} to {int}`, `set datepicker to {string}`, `set slider to {int}`, `set slider {string} to {int}`, `set slider {word} to {int}`, `set input {string} to {string}`, `set input {string} to {word}`, `set input {word} to {string}`, `set input {word} to {word}`

**Navigation:** `go back`, `hide keyboard`

**Observation:** `see tree`, `see {string}`, `see {word}`

**Screenshot:** `screenshot`, `screenshot {string}`, `screenshot {word}`

**Hooks (regex):** `/^Feature( .+)?$/`, `/^Scenario( .+)?$/`, `/^Background( .+)?$/`, `/^Scenario Outline( .+)?$/`, `/^Scenario Template( .+)?$/`

**Wait:** `wait`, `wait {int}`, `wait {int} milliseconds`

### 10.2 Element Resolution Algorithms

#### Click Resolution (`screen/click-resolver`)

Two-pass strategy:

1. **Preferred pass** — clickable elements only, methods tried in order:
   - `description(exact)` + `.clickable(true)`
   - `text(exact)` + `.clickable(true)`
   - `descriptionContains` + `.clickable(true)`
   - `textContains` + `.clickable(true)`

2. **Fallback pass** — any element (no clickable filter):
   - `text(exact)`
   - `description(exact)`
   - `textContains`

Returns first match. Uses `browser.$$()` to check if selector finds any elements.

#### Input Resolution (`screen/input-resolver`)

Four-strategy cascade:

1. **Semantic field matching** — Parse XML page source, find all EditText widgets, score by:
   - Exact hint match (best)
   - Exact text match
   - Exact description match
   - ResourceId suffix match
     Return highest-scored element.

2. **Spatial proximity** — Find all visible text labels matching field name, find all EditText widgets, score each EditText by vertical distance below label + horizontal offset:

   ```
   score = max(verticalGap, 0) + (horizontalOffset * 0.2)
   ```

   Reject inputs above the label. Reject inputs >80px horizontal offset. Lowest score wins.

3. **Direct EditText selectors** — Try text/description/textContains restricted to EditText class.

4. **Fallback selectors** — Try text/resourceId/description/textContains on any element.

### 10.3 How Step Patterns Are Contributed

Each step pattern is a `RegisteredStep` appended to the `step/registry` list service via extension. Step patterns are **external modules** — not part of the base project. The base project defines only the empty registry and infrastructure.

```
step/registry = []                                    (defined by steps core module)
step/registry += [click, type, scroll, ...]           (extended by @uny/steps-mobile — EXTERNAL)
step/registry += [custom-pattern]                     (extended by user's own module)
```

### 11.2 Debug Provider — Extension-Based Tracing

## 12. Session Persistence and Recovery

### 12.1 Session File Format (`.e2e-active-session`)

```json
{
  "id": "abc123-session-id",
  "url": "http://localhost:4723/",
  "capabilities": { "platformName": "Android" },
  "createdAt": "2026-06-20T12:00:00.000Z"
}
```

### 12.2 Session Lifecycle

1. **create()**: Call `webdriverio.remote({hostname, port, path, capabilities, logLevel})`. Get `browser.sessionId`. Persist to file.
2. **attach()**: Read file, call `webdriverio.attach({sessionId, ...})`. Verify alive.
3. **isAlive()**: Call `browser.getTimeouts()` — if returns without error, session is alive.
4. **ensure()**: Try `current()` → `attach()` → `create()`.
5. **close()**: Call `browser.deleteSession()`, delete session file.

### 12.3 Step-Level Session Recovery

Each `StepContext.session()` call:

1. Try `sessionManager.current()` (in-memory)
2. If null, try `sessionManager.attach()` (from file)
3. If that fails, `sessionManager.create()` (fresh)
4. Execute callback
5. On `SessionDeathError` (matched against `session/death-patterns`): create fresh session, retry callback **once** (tracked per step instance via boolean flag — no double-retry)

### 12.4 Custom Errors

## 13. CLI Commands

### `uny run [files...] [options]`

Options: `--new-session`, `--reset <hard|soft|none>`, `--continue-on-error`, `--force`, `-s/--screenshot`, `-t/--tree`, `--format <human|json>`, `-v` (repeatable), `-q` (repeatable), `--debug`

Flow:

1. Generate run ID (ISO timestamp)
2. Create output directory (`output/runs/<runId>/`)
3. Acquire lock via `lock/manager`
4. If `--new-session`, call `session/manager.create()`
5. Determine input: files → multiFileStream | no files → stdin
6. For JSON format, output opening `[`
7. For each line: parse via `parser/gherkin` → skip non-sentences → resolve via `step/resolver` → execute via `step/runner` → append auto-metadata (tree/screenshot) → format via `output/formatter` → write to `io/stdout`
8. For JSON format, output closing `]`
9. Release lock

### `uny tree [options]`

Options: `--format <human|json|xml>`, `--filter <minimal|default|full>`

### `uny reset [mode]`

Modes: `hard`, `soft`. Resolves `reset/executor` and calls it.

### `uny screenshot [label]`

Takes screenshot via session, saves to output directory.

### `uny inspect [key]`

Diagnostic command. Lists all keys with their defining module and extension count, or inspects a single key showing full resolution chain.

## 15. Testing Strategy

### 15.1 Principle

Prove the di library works in principle with a small set of focused tests. Then test real behavior through functional/integration tests at sane boundaries. Don't exhaustively prove wiring — prove behavior.

### 15.2 Composition Library Tests (prove it works in principle)

A small focused suite for the di library itself (`packages/di/tests/`). These prove the primitives are correct — once proven, you trust them and test real modules through their behavior. Uses `node:test` with `node:assert/strict` and tsx loader.

```typescript
import { describe, it } from "node:test";
import assert from "node:assert/strict";
import { composeProviders, DelegatingContainer } from "@uny/di";

// Override: later definition wins
describe("override semantics", () => {
```

### 15.3 Functional Tests (real behavior at sane boundaries)

These test that modules work together correctly. Use a test helper that bootstraps the real module set with a mock device/session override provider appended last.

#### Parity through bootstrap

The `bootstrap` function (see Section 7) is the mechanism that achieves test/production parity. In production the host calls it with the real ordered provider list. In tests the same function is called with the same ordered provider list, plus one extra override provider appended at the end. Because later providers win for definition conflicts, test overrides replace any key without touching module code.

This means:
- All real composition semantics (order, extensions, aliases, caching) execute identically in tests and production.
- Tests do not re-implement wiring — they compose the real thing and substitute only what cannot run in CI (device adapters, real config files, real sessions).
- The override mechanism in tests is identical to the mechanism used in production (e.g. CLI flag override provider, debug override provider). No test-only magic.

The bootstrap function must be a pure, importable utility — not buried inside the CLI entry point — precisely so tests can call it directly.

```typescript
// bootstrap.ts (pure function, importable by both CLI host and tests)
export function bootstrap(
  providers: Map<string, Provider>,
  additionalContainers: Container[] = []
): Container {
  const composed = composeProviders(providers);
  const proxy = new ProxyContainer();
  const delegating = new DelegatingContainer(composed, proxy);
  const detected = new CircularDetector(delegating);
  const appContainer = new CachingContainer(
    new CompositeContainer([...additionalContainers, detected])
  );
  proxy.setInnerContainer(appContainer);
  return appContainer;
}
```

## 19. Future Features (not in scope, but architecture must allow)

These are **not** implementation targets for this plan. The provider/container architecture must allow each to be added as a separate package/provider composed in later, with zero changes to core.

### 19.1 Record / Replay

Record interactive sessions as replayable step sequences:

- `uny record` — start recording mode. Each user interaction is captured as a Gherkin step and written to a feature file in real time.
- `uny replay <file>` — play back a recorded session. Equivalent to `uny run` but the mental model is "this was recorded, now re-execute it".
- Recorded steps include element identifiers (accessibility IDs, resource IDs, XPath) snapshotted at record time.

**Architecture requirement**: a `record` provider that extends `step/runner` to capture executed steps, and a `replay` provider that reads recorded files. Both compose into the existing provider set without modifying core step/session/device packages.

### 19.2 Element ID Locking and Auto-Heal

Lock element identifiers from a recorded or manually-defined session, then detect and auto-update broken selectors on replay:

- When a locked element ID fails to resolve, the runner searches the current tree for the most likely match (by text content, position, type, or semantic similarity).
- If a confident match is found, the locked ID is updated in the recorded file automatically. If not, the step fails with a diff showing what changed.
- Provides a `uny heal <file>` command to batch-heal all broken selectors in a recorded session without re-running it.

**Architecture requirement**: a `heal` provider that extends `screen/selector-builder` with fallback resolution strategies and extends the recording format with locked selector metadata. No changes to core screen/step packages.

### 19.3 REPL Mode (much later)

Interactive REPL for live exploration:

- `uny repl` — start a persistent prompt loop. Type steps, see results immediately. History, tab completion, tree inspection inline.
- Useful for exploratory testing, debugging element selectors, and building feature files interactively.

**Architecture requirement**: a `repl` provider that composes `cli`, `session`, `steps`, and `screen/tree-formatter` into an interactive loop. The existing stdin mode (`uny run <<< '...'`) is the minimal precursor — REPL adds persistence, history, and inline feedback.
